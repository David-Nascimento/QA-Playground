    Guia do especialista

    Pergunta que este cenário responde: o cliente desiste na hora certa e tenta de novo sem piorar a situação? Timeout curto demais gera falhas falsas; longo demais deixa o usuário preso. Retry mal feito multiplica a carga justamente quando o servidor está fraco.

    Hipótese de teste

    Com timeout de 2000 ms e latência de 1500 ms, nenhuma requisição deveria expirar. Ao subir a latência para 2500 ms, todas expiram e cada uma é repetida até o máximo de retries: 5 requisições × (1 tentativa + 2 retries) = 15 tentativas, todas expiradas. Como as requisições rodam em série, o teste leva cerca de 37 s.

    O que medir

    TimeoutsDevem acontecer só quando latência > timeout.
    Retries executadosNunca acima de requisições × máximo de retries.
    Tempo até desistirTimeout × (1 + retries) + esperas entre tentativas.
    Intervalo entre tentativasAqui é fixo em 500 ms. Em produção, deve crescer (backoff) e variar entre clientes (jitter).

    Critério de aceite (exemplo)

    Com latência de 2500 ms, timeout de 2000 ms e 2 retries, o contador de retries chega a exatamente 10, o de timeouts a 15 e o de sucessos fica em 0. Nenhuma tentativa extra depois disso. Desafio: no fim, "Requisições Totais" mostra 15, embora só 5 requisições tenham sido feitas. Isso é um bug? Escreva o relato.

    Armadilhas comuns

    • As requisições deste cenário são simuladas no navegador com setTimeout: elas não aparecem na aba Network. Para tráfego de rede real, use a API mock (npm run dev:api) com o cenário ?scenario=timeout.
    • Retry imediato e sincronizado: todos os clientes voltam ao mesmo tempo e derrubam o servidor de novo (veja o laboratório abaixo).
    • Repetir operações que não são idempotentes, como um pagamento, sem chave de idempotência.
    • Timeout no cliente maior que o do servidor ou do gateway: o usuário espera por uma resposta que nunca vem.

    Automatize com Playwright

    Verifique o limite de retries com valores fixos, para o teste ser determinístico.

    import { test, expect } from '@playwright/test';

test('respeita o máximo de retries quando tudo expira', async ({ page }) => {
  test.setTimeout(60_000); // 5 requisições em série, cada uma com 3 tentativas de 2 s
  await page.goto('/pages/tools/nft/resilience-timeout-retry.html');
  await page.fill('#timeout-value', '2000');
  await page.fill('#latency-value', '2500');   // sempre acima do timeout
  await page.fill('#request-count', '5');
  await page.fill('#max-retries', '2');
  await page.locator('#auto-retry').check();

  await page.click('#start-test');

  // 5 requisições x 2 retries = 10 retries, nenhum sucesso
  await expect(page.locator('#metric-retries')).toHaveText('10', { timeout: 45_000 });
  await expect(page.locator('#metric-timeout')).toHaveText('15', { timeout: 10_000 });
  await expect(page.locator('#metric-success')).toHaveText('0');
});

    Como Testar Este Cenário

    • Timeout: Observe se as requisições são canceladas após o timeout
    • Retry: Verifique se o sistema tenta novamente após timeout
    • Limite de Retries: Teste se o sistema respeita o limite máximo de retries
    • Feedback: Observe mensagens de erro e feedback ao usuário
    • Comportamento: Teste diferentes combinações de timeout e latência
