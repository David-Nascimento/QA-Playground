Fundamentos de Testes de API

Conceitos essenciais sobre APIs REST, SOAP, GraphQL e estrutura de requisições e respostas para QA Engineers.

O que é uma API REST?

Representational State Transfer (REST) é um estilo arquitetural que define princípios para comunicação entre sistemas. APIs REST utilizam métodos HTTP padrão (GET, POST, PUT, DELETE) e retornam dados tipicamente em JSON, embora outros formatos sejam suportados.

Princípios fundamentais:

  • Stateless: Cada requisição é independente e contém todas as informações necessárias para processamento
  • Cacheável: Respostas podem ser cacheadas, reduzindo latência e carga no servidor
  • Interface uniforme: Uso consistente de métodos HTTP padrão e recursos identificados por URIs
  • Cliente-Servidor: Separação de responsabilidades permite evolução independente
  • Sistema em camadas: Arquitetura pode incluir proxies, gateways e balanceadores sem afetar comunicação

REST vs SOAP vs GraphQL (Visão QA)

REST

Características: Arquitetura baseada em HTTP, stateless, cacheável, múltiplos formatos de dados (JSON, XML).

Foco de testes: Métodos HTTP e semântica, códigos de status, estrutura de payloads, headers HTTP, idempotência, cache.

Vantagens para QA: Ferramentas maduras (Postman, Insomnia, curl), documentação OpenAPI/Swagger, testes simples e diretos.

SOAP

Características: Protocolo baseado em XML, contrato rígido via WSDL, transporte independente (HTTP, SMTP, etc.).

Foco de testes: Estrutura de envelopes SOAP, namespaces XML, validação contra schema XSD, headers SOAP (Action, To), fault codes.

Vantagens para QA: Contrato formal (WSDL) define estrutura completa, validação forte de tipos, ferramentas de geração de testes.

GraphQL

Características: Query language, endpoint único, cliente especifica campos necessários, schema tipado.

Foco de testes: Estrutura de queries/mutations, validação de schema, depth limiting (prevenção de queries complexas), rate limiting por query, fragmentos e variáveis.

Vantagens para QA: Introspection permite descobrir schema, flexibilidade para testar diferentes combinações de campos, validação de tipos em tempo de execução.

Estrutura de uma Requisição

Method (Método HTTP)

Define a operação a ser executada no recurso. Métodos principais: GET (leitura), POST (criação), PUT (substituição completa), PATCH (atualização parcial), DELETE (remoção). Métodos auxiliares: OPTIONS (métodos permitidos), HEAD (metadados sem body).

Exemplo: GET, POST, PUT

Endpoint (URI)

Identificador único do recurso. Composto por path (caminho do recurso) e opcionalmente query string (parâmetros de consulta). Path parameters identificam recursos específicos, query params filtram ou modificam a resposta.

Exemplos:

  • GET /api/users/123 — Recurso específico
  • GET /api/users?status=active&page=1 — Lista com filtros

Headers (Cabeçalhos HTTP)

Metadados que fornecem contexto sobre a requisição. Headers essenciais: Content-Type (formato do body), Authorization (credenciais), Accept (formato esperado na resposta), User-Agent (identificação do cliente).

Exemplo:

Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Accept: application/json
X-API-Key: abc123def456

Query Parameters

Parâmetros opcionais na URL após ?, separados por &. Usados para filtros, paginação, ordenação, inclusão de recursos relacionados.

Exemplos:

  • ?page=1&limit=10 — Paginação
  • ?sort=name&order=asc — Ordenação
  • ?include=profile,address — Inclusão de recursos relacionados

Request Body

Dados enviados no corpo da requisição. Formato definido pelo Content-Type. Comum: application/json, application/xml, application/x-www-form-urlencoded, multipart/form-data.

Exemplo JSON:

{
  "name": "João Silva",
  "email": "joao@example.com",
  "age": 30,
  "active": true
}

Estrutura de uma Resposta

Status Code

Indicador numérico de três dígitos que comunica o resultado da requisição. Primeira validação em qualquer teste. Categorias: 2xx (sucesso), 3xx (redirecionamento), 4xx (erro do cliente), 5xx (erro do servidor).

Exemplos: 200 OK, 201 Created, 400 Bad Request, 404 Not Found, 500 Internal Server Error

Response Headers

Metadados da resposta que fornecem informações sobre o recurso e comportamento do servidor. Headers críticos para validação: Content-Type (formato do payload), Cache-Control (diretivas de cache), ETag (versionamento), Location (URI do recurso criado), X-RateLimit-* (controle de taxa).

Validações importantes: Content-Type corresponde ao Accept solicitado, Cache-Control adequado para o tipo de recurso, ETag presente em recursos cacheáveis.

Response Body (Payload)

Dados retornados pela API no formato especificado pelo Content-Type. Estrutura deve seguir o contrato definido (schema JSON, OpenAPI, etc.).

Validações essenciais: Conformidade com schema, tipos de dados corretos, campos obrigatórios presentes, valores dentro dos ranges esperados, regras de negócio aplicadas, ausência de dados sensíveis não autorizados.

Response Time (Latência)

Tempo decorrido entre envio da requisição e recebimento completo da resposta (incluindo headers e body). Métrica crítica para performance e experiência do usuário.

Benchmarks recomendados: GET simples < 200ms, POST/PUT < 500ms, operações complexas < 1s, relatórios/queries pesadas < 5s. Monitorar percentis p50, p95, p99.
