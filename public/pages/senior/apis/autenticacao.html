Autenticação e Autorização

Guia completo sobre métodos de autenticação: API Key, Basic Auth, Bearer Token, OAuth 2.0 e JWT. Como testar cada método.

API Key

Mecanismo: Chave alfanumérica única identificando cliente ou aplicação. Enviada via header customizado (X-API-Key) ou query parameter (menos seguro).

Formato: X-API-Key: abc123def456ghi789 ou ?api_key=abc123def456ghi789

Cenários de teste:

  • Chave válida e ativa → 200 OK
  • Chave inválida (formato incorreto) → 401 Unauthorized
  • Chave ausente → 401 com mensagem clara
  • Chave expirada → 401 com indicação de expiração
  • Chave revogada → 401 com indicação de revogação
  • Chave de ambiente diferente (dev key em prod) → 401
  • Chave com permissões insuficientes → 403 Forbidden

Pontos de falha: Chave expirada sem renovação, chave revogada mas ainda em uso, rate limit específico por chave não respeitado, permissões granulares por chave não validadas.

Vulnerabilidades comuns: Chave em query parameter (exposta em logs, histórico, referrers), ausência de rotação periódica, chaves sem expiração, chaves com permissões muito amplas.

HTTP Basic Authentication

Mecanismo: Credenciais (username:password) codificadas em Base64 e enviadas no header Authorization. Esquema definido em RFC 7617.

Formato: Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ= (onde a string é base64(username:password))

Cenários de teste:

  • Credenciais válidas → 200 OK
  • Username incorreto → 401 Unauthorized
  • Password incorreto → 401 Unauthorized
  • Header Authorization ausente → 401 com WWW-Authenticate: Basic
  • Base64 malformado → 401
  • Caracteres especiais na senha (:, @, etc.) → Validar encoding correto
  • Usuário desativado → 401 ou 403 dependendo da implementação

Pontos de falha: Senha alterada sem invalidar sessões, usuário desativado mas autenticação ainda funciona, encoding UTF-8 vs ASCII, timeout de sessão não implementado.

Vulnerabilidades comuns: Uso em HTTP sem criptografia (credenciais em texto claro), ausência de rotação de senha, falta de rate limiting permite brute force, ausência de account lockout após tentativas falhas.

Bearer Token (JWT ou Opaque)

Mecanismo: Token de acesso (JWT auto-contido ou token opaco) enviado no header Authorization usando esquema Bearer. Definido em RFC 6750.

Formato: Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Cenários de teste:

  • Token válido e não expirado → 200 OK
  • Token expirado (claim exp no passado) → 401 Unauthorized
  • Token inválido (assinatura incorreta) → 401
  • Token ausente → 401 com WWW-Authenticate: Bearer
  • Token malformado (estrutura incorreta) → 401
  • Token de outro usuário acessando recurso privado → 403 Forbidden
  • Token revogado (em blacklist) → 401
  • Algoritmo alterado (alg: none ou alg diferente) → 401

Pontos de falha: Token expirado sem mecanismo de refresh, token revogado mas ainda aceito, assinatura não validada corretamente, claims modificados após emissão, algoritmo de assinatura fraco ou não validado.

Vulnerabilidades comuns: Token em query parameter (exposto em logs), ausência de refresh token mechanism, validação de assinatura permite algoritmo "none", secrets fracos ou expostos, falta de validação de expiração (exp claim).

OAuth 2.0

Mecanismo: Framework de autorização que permite aplicações obter acesso limitado a recursos. Define fluxos de autorização, tokens de acesso e refresh tokens. Especificado em RFC 6749.

Fluxos (Grant Types):

  • Authorization Code: Para aplicações web server-side. Mais seguro, código trocado por token no backend.
  • Implicit: Para SPAs (deprecado em favor de Authorization Code com PKCE). Token retornado diretamente.
  • Client Credentials: Para comunicação machine-to-machine. Sem envolvimento do usuário.
  • Resource Owner Password: Para aplicações altamente confiáveis. Credenciais do usuário trocadas por token.
  • PKCE: Extensão para Authorization Code, adiciona segurança para clientes públicos.

Cenários de teste (Authorization Code):

  • Fluxo completo: obter authorization code → trocar por access token → usar token
  • Refresh token: usar refresh token para obter novo access token
  • Escopos: validar que apenas recursos com escopo adequado são acessíveis
  • Expiração: access token e refresh token expiram corretamente
  • Redirect URI: URI não registrada → rejeição
  • State parameter: ausente ou inválido → rejeição (proteção CSRF)
  • Client credentials: client_id/secret incorretos → 401
  • Code reuse: código usado duas vezes → rejeição

Pontos de falha: Token expirado sem refresh mechanism, escopo insuficiente para operação, redirect_uri não validado permite token theft, client_id/secret comprometidos, state parameter não validado permite CSRF.

Vulnerabilidades comuns: State parameter não validado (CSRF), redirect_uri não validado permite authorization code interception, escopos muito amplos (excesso de permissões), PKCE não implementado em clientes públicos, tokens não revogados após logout.

JWT (JSON Web Token)

Mecanismo: Token auto-contido composto por três partes (header.payload.signature) codificadas em Base64URL. Claims no payload definem identidade, permissões e metadados. Especificado em RFC 7519.

Estrutura: base64url(header).base64url(payload).base64url(signature)

Componentes:

  • Header: Algoritmo de assinatura (alg) e tipo de token (typ: JWT)
  • Payload: Claims (sub, exp, iat, roles, custom claims)
  • Signature: Assinatura criptográfica validando integridade

Cenários de teste:

  • Estrutura válida com três partes separadas por ponto
  • Claims padrão: exp (expiração), iat (emitido em), sub (subject), aud (audience)
  • Claims customizados: roles, permissions, scopes
  • Assinatura válida com secret/chave correta
  • Expiração: token com exp no passado → 401
  • Algoritmo: validar apenas algoritmos permitidos (HS256, RS256)
  • Token modificado: alterar payload e reenviar → 401 (assinatura inválida)
  • Algoritmo alterado: mudar alg no header → 401
  • Secret/key incorreta → 401

Pontos de falha: Token expirado sem refresh, assinatura não validada permite tokens modificados, algoritmo "none" aceito, claims modificados após emissão, secret/chave fraca ou exposta.

Vulnerabilidades comuns: Validação de algoritmo não restrita permite "none" (sem assinatura), ausência de validação de expiração (exp claim), secrets fracos (curtos ou previsíveis), chaves públicas expostas, falta de validação de audience (aud claim), claims críticos não validados.
