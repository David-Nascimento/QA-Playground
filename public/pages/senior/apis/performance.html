Performance e Confiabilidade

Testes não funcionais: tempo de resposta, carga, timeout, retry e resiliência em APIs.

Tempo de Resposta (Latência)

Métrica fundamental para experiência do usuário e eficiência do sistema. Valide latência aceitável conforme tipo de operação e identifique endpoints com degradação de performance.

Benchmarks recomendados:

  • GET simples (cache hit): < 50ms
  • GET simples (cache miss): < 200ms
  • POST/PUT (criação/atualização): < 500ms
  • Operações complexas (cálculos, múltiplas queries): < 1s
  • Relatórios/Queries pesadas (agregações, joins complexos): < 5s
  • Operações assíncronas (202 Accepted): Aceitação < 100ms, processamento conforme SLA

Métricas a monitorar: p50 (mediana), p95, p99, p99.9. Identifique outliers, endpoints problemáticos, degradação ao longo do tempo. Compare latência entre ambientes (dev, staging, prod).

Ferramentas: Postman (Response Time), Apache Bench (ab), JMeter, k6, Artillery, curl com time measurement, ferramentas de APM (Application Performance Monitoring).

Testes de Carga

Valide comportamento da API sob carga através de múltiplas requisições simultâneas. Identifique pontos de falha, degradação de performance e race conditions.

Cenários de teste:

  • Carga baixa: 10-50 usuários simultâneos, validar que performance mantém-se estável
  • Carga média: 50-100 usuários simultâneos, identificar início de degradação
  • Carga alta: 100+ usuários simultâneos, validar que API não quebra completamente
  • Throughput: 100-1000 requisições/segundo, validar taxa de sucesso mantém-se alta
  • Pico de tráfego: Aumento súbito de carga, validar recuperação após pico

Validações obrigatórias:

  • Taxa de sucesso mantém-se acima de 95% sob carga
  • Race conditions não causam corrupção de dados (criação duplicada, atualização concorrente)
  • Rate limiting funciona corretamente sob carga
  • Degradação graceful: API reduz funcionalidades opcionais mas mantém core funcionando
  • Sem memory leaks ou consumo crescente de recursos
  • Connection pooling adequado (não exaure conexões)

Timeout

Valide timeout configurado e comportamento quando timeout ocorre.

O que validar:

  • Timeout configurado (ex: 30s para operações longas)
  • Comportamento quando timeout ocorre (504 Gateway Timeout)
  • Se retry é necessário após timeout
  • Timeout muito curto (operações legítimas falhando)
  • Timeout muito longo (recursos presos)

Testes: Simular operação lenta, validar resposta 504, verificar se operação continua em background.

Retry e Resiliência

Implementação de retry automático em falhas temporárias aumenta confiabilidade. Valide estratégia de retry, backoff e idempotência para evitar efeitos colaterais.

Validações obrigatórias:

  • Retry apenas em falhas temporárias: 503 Service Unavailable, 502 Bad Gateway, 504 Gateway Timeout, 429 Too Many Requests (com Retry-After)
  • Não fazer retry em 4xx (erro do cliente): 400, 401, 403, 404, 422 (não são temporários)
  • Exponential backoff: tempo de espera aumenta exponencialmente (1s, 2s, 4s, 8s, 16s)
  • Jitter: variação aleatória no backoff previne thundering herd problem
  • Máximo de tentativas: limite definido (ex: 3-5 tentativas) antes de falhar definitivamente
  • Idempotência: retry não causa efeitos colaterais (uso de idempotency keys, métodos idempotentes)
  • Timeout por tentativa: evitar que retry trave indefinidamente

Estratégias avançadas: Exponential backoff com jitter, circuit breaker (abre após muitas falhas), retry com idempotency key, retry apenas em métodos seguros (GET, HEAD) ou idempotentes (PUT, DELETE).

Resiliência e Tolerância a Falhas

Sistemas resilientes continuam funcionando mesmo quando dependências falham. Valide estratégias de fallback, circuit breaker e degradação graceful.

Validações obrigatórias:

  • Comportamento quando upstream está down: API retorna resposta apropriada (503, fallback, ou erro claro) sem travar
  • Circuit Breaker: Abre após threshold de falhas, fecha após período de recuperação, half-open state para testar recuperação
  • Fallback: Resposta alternativa quando serviço crítico falha (cache, dados default, resposta simplificada)
  • Degradação graceful: Funcionalidades opcionais desabilitadas, core continua funcionando
  • Health checks: Endpoint /health retorna status de dependências, permite detecção proativa de problemas
  • Auto-recuperação: Sistema detecta e recupera automaticamente quando dependência volta
  • Bulkhead: Isolamento de recursos previne que falha em uma área afete outras

Padrões de resiliência: Circuit Breaker (prevenção de cascata de falhas), Bulkhead (isolamento), Timeout (evitar espera indefinida), Retry (tentativas automáticas), Fallback (resposta alternativa), Health Check (monitoramento de dependências).
