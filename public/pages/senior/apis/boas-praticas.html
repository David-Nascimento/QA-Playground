Como escrever casos de teste de API

Estrutura do caso de teste

Documente caso de teste de forma clara e reproduzível:

  • ID e título: Identificador único e descrição clara do cenário
  • Pré-condições: Dados necessários no sistema, autenticação requerida, estado inicial do sistema
  • Dados de entrada: Endpoint completo, método HTTP, headers (Authorization, Content-Type, etc.), request body (JSON completo), query parameters
  • Ação: Executar requisição HTTP com dados especificados
  • Resultado esperado: Status code HTTP, estrutura do response body (schema), valores específicos esperados, headers de resposta relevantes
  • Validações: Conformidade com schema (JSON Schema), tipos de dados corretos, regras de negócio aplicadas, headers obrigatórios presentes
  • Pós-condições: Estado do sistema após execução, dados criados/modificados

Validações essenciais em cada teste

  • Status code: Código HTTP correto conforme especificação (200, 201, 400, 401, etc.)
  • Schema validation: Estrutura JSON conforme contrato (OpenAPI, JSON Schema), tipos de dados corretos
  • Valores específicos: IDs retornados, timestamps, valores calculados, campos gerados pelo servidor
  • Headers: Content-Type correto, Location (quando aplicável), Cache-Control, ETag, X-RateLimit-*
  • Performance: Tempo de resposta dentro dos limites aceitáveis
  • Idempotência: Quando aplicável, validar que requisições idênticas produzem mesmo resultado

Cenários obrigatórios a cobrir

  • Happy path: Fluxo principal com dados válidos, todas as condições ideais
  • Validações de entrada: Campos obrigatórios ausentes, tipos incorretos, formatos inválidos, valores fora de range
  • Erros esperados: 400 (bad request), 401 (unauthorized), 403 (forbidden), 404 (not found), 409 (conflict), 422 (validation failed), 429 (rate limit)
  • Edge cases: Valores limites (min, max), strings vazias, null, arrays vazios, objetos vazios
  • Testes negativos: Payload malformado, autenticação inválida, permissões insuficientes, injeção de código
  • Concorrência: Requisições simultâneas, race conditions, atualizações concorrentes

Como estruturar coleções (Postman / Insomnia)

Organização

  • Por funcionalidade: Users, Products, Orders (agrupa endpoints relacionados)
  • Por endpoint: GET /users, POST /users, PUT /users/:id
  • Por fluxo de negócio: Criar usuário → Atualizar → Deletar

Variáveis

  • Base URL: {{baseUrl}} (ex: https://api.example.com)
  • Tokens: {{accessToken}} (atualizado automaticamente)
  • IDs dinâmicos: {{userId}} (salvo de resposta anterior)
  • Dados de teste: {{testEmail}}, {{testPassword}}

Ambientes

  • Dev: Desenvolvimento (dados de teste, menos restritivo)
  • QA: Testes (dados isolados, limpos periodicamente)
  • Staging: Pré-produção (dados mais próximos de prod)
  • Production: Apenas leitura (GET apenas, sem modificações)

Testes automatizados

Implemente validações automáticas em cada requisição para garantir qualidade e reduzir trabalho manual:

  • Assertions: Validar status code, schema JSON, tipos de dados, valores específicos, headers obrigatórios, tempo de resposta
  • Scripts (Pre-request): Gerar dados dinâmicos, calcular timestamps, criar tokens temporários, preparar payloads
  • Scripts (Tests): Extrair valores da resposta (tokens, IDs), salvar em variáveis de ambiente, executar lógica condicional, validar regras de negócio
  • Chain de requests: Usar resposta de uma requisição na próxima (ex: criar usuário → usar ID para atualizar → deletar)
  • Validação de schema: Validar estrutura JSON contra JSON Schema ou OpenAPI contract
  • Validação de performance: Verificar tempo de resposta dentro de limites aceitáveis

Exemplo: Postman Test Script Completo

// Validações básicas
pm.test('Status code is 201', () => {
    pm.response.to.have.status(201);
});

pm.test('Response time < 500ms', () => {
    pm.expect(pm.response.responseTime).to.be.below(500);
});

// Validação de schema
pm.test('Response has correct structure', () => {
    const jsonData = pm.response.json();
    pm.expect(jsonData).to.have.property('data');
    pm.expect(jsonData.data).to.have.property('id');
    pm.expect(jsonData.data).to.have.property('name');
    pm.expect(jsonData.data).to.have.property('email');
});

// Extrair e salvar valores
const userId = pm.response.json().data.id;
pm.environment.set('createdUserId', userId);

// Validação de regra de negócio
pm.test('Email format is valid', () => {
    const email = pm.response.json().data.email;
    pm.expect(email).to.match(/^[^\s@]+@[^\s@]+\.[^\s@]+$/);
});

// Validação de headers
pm.test('Location header present', () => {
    pm.expect(pm.response.headers.get('Location')).to.exist;
});

Documentação

  • Descrição do endpoint e propósito
  • Exemplos de requisição e resposta
  • Pré-requisitos (autenticação, dados necessários)
  • Possíveis erros e como resolver

Como organizar ambientes

Separação de ambientes

  • Dev: Desenvolvimento ativo, dados podem ser resetados
  • QA: Testes manuais e automatizados, dados isolados
  • Staging: Pré-produção, validação final antes de deploy
  • Production: Ambiente real, apenas leitura para testes

Dados de teste

  • Dados isolados por ambiente (não compartilhar entre Dev e QA)
  • Limpeza periódica (evitar acúmulo de dados de teste)
  • Seed scripts para popular dados iniciais
  • Dados conhecidos e documentados (ex: usuário admin padrão)

Configuração

  • Variáveis de ambiente (URLs, credenciais)
  • Secrets gerenciados (não commitar no código)
  • Documentação de acesso (como obter credenciais)
  • Versionamento de APIs (v1, v2, etc.)

Como reportar bugs de API corretamente

Informações obrigatórias no bug report

  • Endpoint completo: POST /api/v1/users (incluir versão da API se aplicável)
  • Método HTTP: GET, POST, PUT, PATCH, DELETE, etc.
  • Headers enviados: Content-Type, Authorization, Accept, X-API-Key, etc. (valores mascarados se sensíveis)
  • Request body: JSON completo formatado, sem dados sensíveis (senhas, tokens completos)
  • Query parameters: Todos os parâmetros enviados na URL
  • Base URL: Ambiente e domínio completo

Resposta recebida (completa)

  • Status code: Código HTTP recebido (400, 500, etc.)
  • Response headers: Content-Type, Location, X-RateLimit-*, Retry-After, etc.
  • Response body: JSON completo de erro ou resposta inesperada (formatado para legibilidade)
  • Response time: Tempo de resposta em milissegundos (especialmente se muito lento ou timeout)
  • Timestamp: Data e hora exata da requisição (UTC)

Comportamento esperado vs atual

  • Comportamento esperado: O que deveria acontecer conforme documentação (OpenAPI/Swagger), contrato ou especificação
  • Comportamento atual: O que realmente aconteceu, descrito de forma objetiva
  • Evidências: Screenshots de ferramentas (Postman, Insomnia), logs do servidor (se disponível), curl command completo, response salvo em arquivo
  • Impacto: Como o bug afeta usuários, integrações ou processos de negócio

Contexto e reprodutibilidade

  • Ambiente: Dev, QA, Staging, Production (especificar versão se aplicável)
  • Dados de teste: IDs, emails, tokens (mascarados) usados na reprodução
  • Passos para reproduzir: Sequência numerada, clara e completa (incluir pré-condições)
  • Frequência: Sempre (100%), às vezes (intermitente), primeira vez, após ação específica
  • Workaround: Se existe forma de contornar o problema temporariamente

Classificação de severidade

Baseie severidade no impacto no negócio e usuários, não apenas no tipo técnico do erro:

  • Bloqueante (P0): Impede uso completo da funcionalidade, sem workaround viável
  • Alta (P1): Impacto significativo na funcionalidade, mas há workaround ou funcionalidade parcial funciona
  • Média (P2): Impacto moderado, funcionalidade parcial ou degradada, workaround disponível
  • Baixa (P3): Impacto mínimo, questão cosmética, erro em caso edge, não afeta fluxo principal

Exemplo: Erro 500 em endpoint crítico de pagamento = Bloqueante. Erro 500 em endpoint de relatório opcional = Alta ou Média dependendo do uso.
