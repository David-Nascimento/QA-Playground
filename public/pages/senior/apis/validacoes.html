Validações Essenciais em Testes de API

Checklist prático para garantir cobertura completa em testes de API: schema, tipos, campos, regras de negócio e mais.

Validação de Contrato (Schema)

Validação contra contrato formal define estrutura esperada, tipos de dados e regras. Utilize JSON Schema, OpenAPI/Swagger, ou contrato definido pela equipe.

Validações obrigatórias:

  • Estrutura do JSON conforme schema (propriedades, objetos aninhados, arrays)
  • Tipos de dados corretos (string, number, integer, boolean, array, object, null)
  • Campos obrigatórios presentes (required array validado)
  • Campos opcionais tratados corretamente (ausentes vs null vs valores default)
  • Formatos validados (date, email, uri, uuid, regex patterns)
  • Constraints aplicadas (min/max length, min/max value, enum values)

Tipos de Dados e Conversões

Valide tratamento correto de tipos primitivos e conversões implícitas. APIs devem rejeitar tipos incompatíveis ou converter explicitamente quando aplicável.

Cenários de teste:

  • String em campo numérico: {"age": "30"} → 400 Bad Request ou conversão explícita
  • Número em campo string: {"id": 123} → Aceitar com conversão ou rejeitar
  • Array vazio em campo que requer elementos: {"tags": []} → 422 se minItems > 0
  • Objeto aninhado com estrutura incorreta: {"address": "string"} → 400 se espera objeto
  • Null em campo não-nullable: {"name": null} → 400 Bad Request

Campos Obrigatórios e Opcionais

Valide comportamento quando campos obrigatórios estão ausentes e tratamento de campos opcionais. Distinga entre campo ausente, null e string vazia.

Cenários de teste:

  • Campo obrigatório ausente: {} sem "email" → 422 Unprocessable Entity
  • Campo obrigatório null: {"email": null} → 400 Bad Request
  • Campo opcional ausente: {"email": "test@example.com"} sem "phone" → 200 OK
  • Campo opcional null: {"phone": null} → 200 OK ou 400 dependendo da política
  • String vazia vs ausente: {"name": ""} vs {} → Comportamento documentado

Regras de Negócio

Validações customizadas que implementam lógica de domínio além de validação estrutural. Teste constraints de unicidade, ranges, formatos específicos e relacionamentos.

Cenários de teste:

  • Email duplicado: {"email": "existente@example.com"} → 409 Conflict
  • Data futura inválida: {"birthDate": "2050-01-01"} → 422 Unprocessable Entity
  • Valor fora de range: {"age": -5} ou {"age": 150} → 422
  • Formato inválido: {"cpf": "123"} → 422 com mensagem específica
  • Relacionamento inválido: {"categoryId": 999} → 422 ou 404 dependendo da implementação

Mensagens de Erro

Mensagens devem ser claras, acionáveis e não expor detalhes técnicos ou estrutura interna. Formato consistente facilita tratamento pelo cliente.

Boas práticas:

  • Boa: {"error": "Email já está em uso", "field": "email"}
  • Ruim: {"error": "UNIQUE constraint failed: users.email"}
  • Boa: {"errors": [{"field": "age", "message": "Idade deve estar entre 0 e 120"}]}
  • Ruim: {"error": "ValidationError: age must be >= 0"}

Estrutura recomendada: Objeto com array de erros, cada erro contendo campo, código, mensagem e valor recebido quando aplicável.

Headers Obrigatórios

Valide presença e formato de headers críticos: Content-Type (formato do body), Authorization (credenciais), Accept (formato esperado na resposta).

Cenários de teste:

  • POST sem Content-Type → 400 Bad Request ou 415 Unsupported Media Type
  • Content-Type incorreto: text/plain em endpoint JSON → 400 ou 415
  • Requisição sem Authorization → 401 Unauthorized
  • Accept: application/xml em endpoint JSON → 406 Not Acceptable ou 200 com formato diferente
  • Authorization malformado → 401 com WWW-Authenticate header

Paginação

Implementação de paginação previne sobrecarga e timeouts. Valide parâmetros (page, limit, offset), metadata retornada e comportamento com valores inválidos.

Validações obrigatórias:

  • Total de registros retornado (total, count) para cálculo de páginas
  • Metadata de paginação (current_page, per_page, total_pages)
  • Links de navegação (first, last, next, prev) quando aplicável
  • Valores inválidos tratados: page=0 ou negativo → 400, limit muito alto → limitado ao máximo
  • Comportamento consistente: última página vazia retorna array vazio, não erro

Ordenação

Valide capacidade de ordenar resultados por um ou múltiplos campos, direção (ascendente/descendente) e tratamento de campos inválidos.

Cenários de teste:

  • Ordenação simples: ?sort=name&order=asc → Resultados ordenados
  • Múltiplos campos: ?sort=name,age&order=asc,desc → Ordenação composta
  • Campo inexistente: ?sort=invalidField → 400 Bad Request
  • Direção inválida: ?order=invalid → 400 ou default para asc
  • Campos não ordenáveis: ?sort=password → 400 (segurança)

Filtros e Query Parameters

Valide capacidade de filtrar resultados usando query parameters, operadores suportados, combinações e proteção contra injection.

Validações obrigatórias:

  • Filtro simples: ?status=active → Apenas recursos com status active
  • Múltiplos filtros: ?status=active&category=tech → AND lógico
  • Operadores: ?age=gt:18, ?price=lt:100 → Maior que, menor que
  • SQL injection: ?filter=1' OR '1'='1 → Rejeitado ou sanitizado
  • NoSQL injection: ?filter[$where]=... → Rejeitado
  • Campos não filtráveis: ?password=test → Ignorado ou 400 (segurança)

Rate Limiting

Controle de taxa previne abuso e garante disponibilidade. Valide headers informativos, comportamento quando limite é excedido e estratégia de retry.

Validações obrigatórias:

  • Headers informativos: X-RateLimit-Limit (limite total), X-RateLimit-Remaining (requisições restantes), X-RateLimit-Reset (timestamp de reset)
  • Status 429 Too Many Requests quando limite excedido
  • Header Retry-After indicando segundos até próximo reset
  • Comportamento após limite: bloqueio temporário, throttling, ou rejeição
  • Limites diferentes por tipo de endpoint (GET vs POST) ou por usuário/API key

Idempotência

Métodos PUT, DELETE e PATCH devem ser idempotentes: múltiplas requisições idênticas produzem mesmo resultado. Crítico para retry automático e resiliência.

Validações obrigatórias:

  • PUT idempotente: duas requisições idênticas resultam em mesmo estado do recurso
  • DELETE idempotente: deletar recurso já deletado retorna 204, não 404
  • PATCH idempotente: aplicar mesmo patch múltiplas vezes = mesmo resultado
  • Idempotency key: header X-Idempotency-Key permite identificar requisições duplicadas
  • POST não é idempotente por padrão, mas pode usar idempotency key para garantir
