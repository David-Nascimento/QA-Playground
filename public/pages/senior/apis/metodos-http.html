Métodos HTTP — Visão de Testes

Guia completo sobre métodos HTTP: quando usar, o que validar e riscos comuns para QA Engineers.

GET

Semântica: Recuperar representação de um recurso. Método idempotente e seguro (não altera estado do servidor).

Uso: Buscar recurso específico, listar coleções, consultas com filtros, operações de leitura.

Validações obrigatórias:

  • Status code 200 OK para sucesso
  • Estrutura do payload conforme schema (JSON Schema, OpenAPI)
  • Headers de cache quando aplicável (Cache-Control, ETag, Last-Modified)
  • Paginação implementada para coleções grandes (page, limit, total)
  • Query parameters funcionando corretamente (filtros, ordenação, inclusão)
  • Idempotência: múltiplas requisições idênticas retornam mesmo resultado

Riscos e vulnerabilidades:

  • Exposição de dados sensíveis em query params (aparecem em logs, histórico do navegador)
  • Ausência de paginação causa timeouts e sobrecarga (retornar milhares de registros)
  • Cache mal configurado retorna dados desatualizados ou privados
  • SQL/NoSQL injection através de filtros não sanitizados
  • Information disclosure através de mensagens de erro detalhadas

POST

Semântica: Criar novo recurso ou executar ação não idempotente. Não é seguro (pode alterar estado) nem idempotente (múltiplas chamadas criam recursos diferentes).

Uso: Criar recursos, ações com efeitos colaterais (enviar email, processar pagamento, disparar notificação), submissão de formulários.

Validações obrigatórias:

  • Status 201 Created quando recurso é criado (com Location header) ou 200 OK para ações
  • Payload retorna recurso criado completo, incluindo ID gerado
  • Location header presente com URI do novo recurso (RFC 7231)
  • Validação completa de campos obrigatórios e tipos
  • Regras de negócio aplicadas (unicidade, constraints, validações customizadas)
  • Headers apropriados (Content-Type validado, CORS se aplicável)

Riscos e vulnerabilidades:

  • Criação duplicada por requisições repetidas (ausência de idempotência)
  • Validação insuficiente permite dados inválidos ou maliciosos
  • Falta de sanitização resulta em XSS, injection (SQL, NoSQL, Command)
  • Exposição de informações sensíveis no response (senhas, tokens internos, stack traces)
  • Mass assignment: aceitar campos não permitidos que modificam estado crítico
  • CSRF quando não há proteção adequada

PUT

Semântica: Substituir recurso completo. Método idempotente: múltiplas requisições idênticas têm mesmo efeito. Pode criar recurso se não existir (upsert).

Uso: Atualização completa de recurso existente, criação/atualização quando ID é conhecido, sincronização de estado.

Validações obrigatórias:

  • Status 200 OK (recurso atualizado) ou 201 Created (recurso criado) ou 204 No Content
  • Recurso substituído completamente: todos os campos atualizados conforme payload
  • Idempotência garantida: requisições idênticas produzem mesmo estado final
  • Campos não enviados são removidos ou definidos como default (comportamento documentado)
  • Validação de todos os campos obrigatórios (mesmo nível de POST)
  • Versionamento (ETag, If-Match) quando aplicável para prevenir race conditions

Riscos e vulnerabilidades:

  • Sobrescrita acidental por falta de validação de versão (lost update problem)
  • Perda de dados quando campos não enviados são removidos (comportamento não documentado)
  • Validação inconsistente entre PUT e POST causa comportamentos inesperados
  • Ausência de autorização permite sobrescrever recursos de outros usuários
  • Race conditions em atualizações concorrentes sem controle de versão

PATCH

Semântica: Aplicar modificações parciais em um recurso. Método idempotente: múltiplas requisições idênticas têm mesmo efeito. Apenas campos presentes no payload são modificados.

Uso: Atualização parcial de recursos, modificações incrementais, evitar retransmissão de dados completos.

Validações obrigatórias:

  • Status 200 OK com recurso atualizado ou 204 No Content
  • Apenas campos enviados são modificados, demais permanecem inalterados
  • Validação dos campos enviados (tipos, formatos, regras de negócio)
  • Idempotência: requisições idênticas produzem mesmo estado
  • Merge correto de estruturas complexas (arrays, objetos aninhados) conforme estratégia definida
  • Suporte a JSON Patch (RFC 6902) ou formato customizado documentado

Riscos e vulnerabilidades:

  • Validação inconsistente permite valores inválidos em atualização parcial
  • Merge incorreto de arrays/objetos causa perda de dados ou estado inconsistente
  • Confusão entre PUT (substituição completa) e PATCH (atualização parcial)
  • Ausência de validação de campos críticos em atualizações parciais
  • Estratégia de merge não documentada causa comportamentos inesperados

DELETE

Semântica: Remover recurso identificado pela URI. Método idempotente: deletar recurso já deletado retorna sucesso (204). Não é seguro (altera estado).

Uso: Remoção de recursos, exclusão lógica ou física, limpeza de dados.

Validações obrigatórias:

  • Status 204 No Content (sucesso sem body) ou 200 OK com confirmação
  • Recurso removido: GET subsequente retorna 404 Not Found
  • Soft delete vs hard delete claramente documentado e testado
  • Remoção em cascata de recursos dependentes (se aplicável) testada
  • Idempotência: deletar recurso inexistente retorna 204 (não 404)
  • Autorização verificada: apenas usuários com permissão podem deletar

Riscos e vulnerabilidades:

  • Remoção em cascata não testada causa orfãos ou violação de integridade referencial
  • Ausência de autorização permite deleção não autorizada (IDOR)
  • Soft delete não documentado causa confusão sobre estado real do recurso
  • Recursos relacionados não tratados (ex: deletar usuário sem tratar pedidos)
  • Ausência de confirmação para operações críticas (deleção em massa)
  • Falta de auditoria/logging de operações de deleção

OPTIONS

Semântica: Obter métodos HTTP permitidos para um recurso. Usado principalmente para CORS preflight requests. Método seguro e idempotente.

Uso: Verificar métodos permitidos antes de requisição real, CORS preflight, descoberta de capacidades da API.

Validações obrigatórias:

  • Header Allow listando métodos permitidos (GET, POST, PUT, etc.)
  • CORS headers corretos quando aplicável (Access-Control-Allow-Methods, Access-Control-Allow-Headers, Access-Control-Allow-Origin)
  • Status 200 OK ou 204 No Content
  • Body vazio ou contendo apenas informações sobre capacidades

Riscos e vulnerabilidades:

  • CORS mal configurado bloqueia requisições legítimas de origens autorizadas
  • Métodos perigosos expostos incorretamente (DELETE, PUT em endpoints públicos)
  • Falta de implementação retorna 405, quebrando CORS preflight
  • Headers CORS muito permissivos (Access-Control-Allow-Origin: *) em produção

HEAD

Semântica: Obter headers de resposta sem body. Comportamento idêntico ao GET, exceto pela ausência de payload. Método seguro e idempotente.

Uso: Verificar existência de recurso, validar cache (ETag, Last-Modified), obter metadados sem transferir dados, verificar tamanho do recurso.

Validações obrigatórias:

  • Status code idêntico ao GET equivalente (200, 404, etc.)
  • Headers idênticos ao GET, especialmente ETag, Last-Modified, Content-Type, Content-Length
  • Body obrigatoriamente vazio (não deve conter payload)
  • Content-Length presente e correto (tamanho do recurso se fosse retornado)

Riscos e vulnerabilidades:

  • Headers inconsistentes com GET causam problemas de cache
  • ETag diferente do GET quebra validação de cache
  • Falta de implementação retorna 405 ou comportamento inesperado
  • Content-Length incorreto afeta download progress e validações
