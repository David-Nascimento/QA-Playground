Status Codes HTTP — Visão Completa para QA

Guia completo de códigos de status HTTP: o que validar, cenários de teste e como reportar corretamente.

2xx — Sucesso

200 OK

Requisição processada com sucesso. Status padrão para GET, PUT, PATCH quando operação completa com sucesso.

Validações: Payload conforme schema, estrutura JSON válida, tipos de dados corretos, campos obrigatórios presentes, regras de negócio aplicadas, headers apropriados (Content-Type, Cache-Control).

201 Created

Recurso criado com sucesso. Deve ser usado em POST quando novo recurso é criado no servidor.

Validações: Location header presente com URI absoluta do recurso criado, ID do recurso retornado no payload, dados completos do recurso criado (incluindo campos gerados pelo servidor), Content-Location header quando aplicável.

202 Accepted

Requisição aceita para processamento assíncrono. Operação será executada posteriormente. Cliente deve verificar status através de endpoint fornecido.

Validações: Endpoint de status retornado (Location ou Link header), ID de processamento/job para rastreamento, documentação de como verificar status (polling, webhook, etc.), tempo estimado de processamento se disponível.

204 No Content

Requisição bem-sucedida sem corpo de resposta. Comum em DELETE e PUT quando não há necessidade de retornar dados.

Validações: Body obrigatoriamente vazio, headers relevantes presentes (ETag, Last-Modified se aplicável), operação realmente executada (verificar estado do recurso), Content-Length: 0 ou header ausente.

O que validar além do status:

  • Estrutura do JSON conforme schema
  • Tipos de dados corretos (string, number, boolean, etc.)
  • Campos obrigatórios presentes
  • Regras de negócio aplicadas
  • Valores dentro dos ranges esperados

3xx — Redirecionamento

301 Moved Permanently

Recurso movido permanentemente para nova URL.

O que validar: Location header com nova URL, cliente segue redirecionamento automaticamente, cache atualizado.

302 Found

Redirecionamento temporário. URL antiga ainda pode ser usada.

O que validar: Location header, comportamento do cliente, se redirecionamento é seguido.

304 Not Modified

Recurso não modificado desde última requisição (cache).

O que validar: ETag ou If-None-Match funcionando, body vazio, headers de cache corretos.

Quando testar: Migrações de endpoints, mudanças de domínio, otimizações de cache.

Riscos: Loops de redirecionamento, perda de dados em redirects, cache incorreto.

4xx — Erros do Cliente (QA ESSENCIAL)

400 Bad Request

Requisição malformada ou sintaticamente incorreta. Erro do cliente que impede processamento.

Validações: Mensagem de erro descritiva, campos problemáticos identificados no payload de erro, orientação sobre como corrigir, estrutura de erro consistente (ex: JSON com "errors" array).

401 Unauthorized

Requisição requer autenticação. Credenciais ausentes, inválidas ou expiradas. Diferente de 403 (autenticado mas sem permissão).

Validações: Header WWW-Authenticate presente indicando esquema de autenticação, mensagem clara sobre necessidade de autenticação, não expõe detalhes sobre credenciais inválidas (evita user enumeration).

403 Forbidden

Cliente autenticado mas sem permissão para acessar o recurso. Servidor entendeu a requisição mas recusa autorizar.

Validações: Diferença clara entre 401 (não autenticado) e 403 (sem permissão), mensagem explicando falta de autorização sem expor estrutura de permissões, não retorna detalhes sobre recursos existentes que o usuário não pode acessar.

404 Not Found

Recurso não encontrado no servidor. Endpoint pode existir mas recurso específico (ID) não foi encontrado, ou endpoint não existe.

Validações: Mensagem genérica que não expõe estrutura interna (ex: "Resource not found" vs "Table users doesn't exist"), comportamento consistente para recursos inexistentes e endpoints inexistentes (ambos 404), não revela se recurso existe mas usuário não tem acesso (deve ser 403).

405 Method Not Allowed

Método HTTP usado não é permitido para este endpoint. Endpoint existe mas método não é suportado.

Validações: Header Allow obrigatório listando métodos permitidos (GET, POST, etc.), mensagem clara indicando método não permitido, status correto mesmo quando método não implementado.

409 Conflict

Conflito com estado atual do recurso. Requisição não pode ser completada devido a conflito (ex: email duplicado, versão desatualizada, recurso bloqueado).

Validações: Mensagem específica explicando natureza do conflito, orientação sobre como resolver (ex: obter versão atual e retentar, usar condicional headers), payload de erro com detalhes do conflito quando aplicável.

422 Unprocessable Entity

Requisição bem formada sintaticamente mas semanticamente incorreta. Validações de negócio falharam.

Validações: Lista estruturada de erros por campo (array de objetos com campo, código, mensagem), mensagens claras e acionáveis, formato consistente (ex: JSON com "errors" contendo array de erros), códigos de erro padronizados quando aplicável.

429 Too Many Requests

Cliente excedeu limite de taxa de requisições (rate limiting). Muitas requisições em período de tempo definido.

Validações: Headers X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset presentes, header Retry-After indicando quando retentar, mensagem clara sobre limite excedido, comportamento após limite (bloqueio temporário, throttling, etc.).

Cenários reais de teste:

  • Payload inválido (JSON malformado, tipos errados)
  • Campos ausentes (obrigatórios não enviados)
  • Valores fora de range (idade negativa, string muito longa)
  • Validações de negócio (email duplicado, data futura inválida)
  • Autenticação/autorização (token inválido, sem permissão)

5xx — Erros do Servidor

500 Internal Server Error

Erro genérico do servidor indicando falha inesperada no processamento. Não deve ser usado para erros de validação ou de negócio.

Validações: Mensagem genérica que não expõe detalhes técnicos (stack traces, caminhos de arquivo, queries SQL), logs detalhados no servidor para debugging, identificador único do erro (error ID) para rastreamento, não expõe informações sensíveis sobre infraestrutura.

502 Bad Gateway

Gateway ou proxy recebeu resposta inválida de servidor upstream. Indica problema de comunicação entre serviços.

Validações: Distinguir entre problema de infraestrutura (upstream down) e aplicação (upstream retornando erro), timeout de upstream documentado, mensagem indica problema temporário quando aplicável, logs no gateway para diagnóstico.

503 Service Unavailable

Serviço temporariamente indisponível devido a manutenção, sobrecarga ou indisponibilidade de dependências. Indica que serviço pode estar disponível novamente após período.

Validações: Header Retry-After presente indicando quando retentar, mensagem clara diferenciando manutenção programada de sobrecarga, status apropriado para circuit breaker aberto, indicação se problema é temporário ou requer ação.

504 Gateway Timeout

Gateway não recebeu resposta de servidor upstream dentro do tempo limite configurado. Timeout ocorreu antes da resposta chegar.

Validações: Timeout configurado e documentado, distinção entre upstream lento vs inacessível, Retry-After quando aplicável, logs indicando qual upstream falhou, mensagem indica que requisição pode ser retentada.

Como simular: Forçar erros no servidor, desconectar serviços upstream, simular timeouts, sobrecarga.

Como reportar: Incluir timestamp, request completo (method, endpoint, headers, body), resposta recebida, logs do servidor (se disponível), frequência do erro.
