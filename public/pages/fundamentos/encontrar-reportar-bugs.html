Módulo 8: Encontrar e Reportar Bugs

Desenvolva habilidades para encontrar bugs de forma eficiente e reportá-los de maneira clara e profissional, seguindo boas práticas da indústria para comunicação efetiva de problemas encontrados.

Como Encontrar Bugs

Encontrar bugs requer uma combinação de método, criatividade e atenção aos detalhes. A seguir estão técnicas e abordagens que ajudam a descobrir problemas no software.

Técnicas para Encontrar Bugs

1. Pense Como um Usuário

Use o sistema como um usuário real faria. Não siga apenas o caminho feliz - explore diferentes formas de usar a aplicação.

Como fazer:

  • Use o sistema sem seguir documentação ou scripts
  • Tente fazer tarefas como um usuário novato faria
  • Pense em diferentes tipos de usuários e como cada um usaria o sistema
  • Observe se há formas não intuitivas de fazer algo
  • Teste fluxos que usuários reais seguiriam

2. Teste Validações

Tente inserir dados inválidos para verificar se o sistema valida adequadamente:

  • Campos vazios: Deixe campos obrigatórios em branco
  • Valores muito grandes: Teste limites de tamanho de campos
  • Caracteres especiais: Use símbolos, emojis, caracteres unicode
  • SQL injection: Teste proteção contra injeção SQL
  • XSS (Cross-Site Scripting): Teste proteção contra scripts maliciosos
  • Tipos incorretos: Insira texto onde se espera número, e vice-versa
  • Valores negativos: Onde não deveriam ser aceitos

3. Teste Casos de Borda

Teste valores nos limites onde bugs são mais prováveis de ocorrer:

  • Valores mínimo e máximo: Teste os limites exatos
  • Zero e valores negativos: Onde aplicável
  • Strings muito longas: Teste limite de caracteres
  • Caracteres especiais e unicode: Diferentes encodings
  • Espaços em branco: Início, meio e fim de strings
  • Números decimais: Precisão e arredondamento
  • Datas extremas: Datas passadas muito antigas, futuras muito distantes

4. Teste Integrações

Verifique como o sistema se comporta quando há problemas com componentes externos:

  • APIs externas falhando: Simule falhas de APIs
  • Timeouts: Quando requisições demoram muito
  • Dados corrompidos: Quando APIs retornam dados inesperados
  • Rede instável: Simule perda de conexão
  • Serviços indisponíveis: Quando serviços externos estão fora do ar

5. Teste em Diferentes Ambientes

Bugs podem aparecer apenas em configurações específicas:

  • Navegadores diferentes: Chrome, Firefox, Safari, Edge
  • Dispositivos diferentes: Desktop, tablet, mobile
  • Sistemas operacionais: Windows, macOS, Linux, iOS, Android
  • Resoluções de tela: Diferentes tamanhos e orientações
  • Versões diferentes: Versões antigas e novas de navegadores
  • Configurações diferentes: Diferentes configurações de acessibilidade, idioma, etc.

6. Use Testes Exploratórios

Explore o sistema livremente, sem seguir scripts. Muitos bugs são encontrados quando você "brinca" com a aplicação:

  • Navegue sem objetivo específico
  • Tente ações inesperadas
  • Use o sistema de forma não convencional
  • Observe comportamentos inesperados
  • Teste rapidamente várias funcionalidades

7. Revise Logs e Console

Muitos bugs não são visíveis na interface, mas aparecem em logs:

  • Console do navegador: Verifique erros JavaScript
  • Network tab: Verifique requisições falhando ou retornando erros
  • Logs do servidor: Erros no backend
  • Ferramentas de debug: Use DevTools para inspecionar problemas

8. Teste Regressão

Execute testes que já passaram anteriormente. Novas funcionalidades podem quebrar funcionalidades existentes:

  • Mantenha uma suíte de testes de regressão
  • Execute após cada release ou mudança significativa
  • Foque em funcionalidades críticas que não devem quebrar

Como Reportar Bugs

Um bug bem reportado é muito mais fácil de ser corrigido. Um report claro e completo economiza tempo para desenvolvedores e acelera a resolução do problema.

Estrutura de um Bom Bug Report

1. Título Claro e Descritivo

O título deve resumir o problema de forma clara e objetiva. Deve ser específico o suficiente para entender o problema sem ler o corpo do report.

Bom exemplo: "Botão de login não responde após 3 tentativas de login inválido"

Mau exemplo: "Erro no sistema"

Dicas para bons títulos:

  • Seja específico sobre o que está quebrado
  • Mencione onde o problema ocorre
  • Inclua condições específicas se relevante
  • Evite termos vagos como "erro" ou "problema"

2. Descrição Detalhada

Descreva claramente o que aconteceu, o que era esperado e o que foi observado:

Passos para Reproduzir

Lista numerada e clara dos passos exatos para reproduzir o bug. Deve ser específica o suficiente para que qualquer pessoa possa seguir:

  1. Acesse a página de login
  2. Insira um email válido
  3. Insira uma senha incorreta
  4. Clique no botão "Entrar"
  5. Repita os passos 2-4 mais duas vezes (total de 3 tentativas)
  6. Na terceira tentativa, tente clicar no botão novamente

Resultado Esperado

O que deveria acontecer se o sistema estivesse funcionando corretamente.

Exemplo: O botão deve continuar respondendo e exibir uma mensagem de erro após a terceira tentativa, bloqueando o acesso temporariamente.

Resultado Atual

O que realmente aconteceu. Seja específico e objetivo.

Exemplo: Após a terceira tentativa, o botão não responde mais ao clique e não há nenhuma mensagem de erro ou feedback visual.

3. Ambiente e Configuração

Inclua informações sobre o ambiente onde o bug foi encontrado. Isso é crucial porque alguns bugs só ocorrem em configurações específicas:

  • Sistema operacional e versão: Windows 11, macOS 14.0, Linux Ubuntu 22.04
  • Navegador e versão: Chrome 120.0, Firefox 121.0, Safari 17.0
  • Versão da aplicação: v2.1.3, build 1234
  • Dispositivo: Desktop, iPhone 14, Samsung Galaxy S23
  • Resolução de tela: 1920x1080, 1366x768
  • Dados de teste utilizados: Email: teste@example.com, senha: senha123

4. Evidências

Anexe evidências visuais e dados que comprovem o problema:

  • Screenshots: Imagens mostrando o problema
  • Vídeos: Gravação da tela mostrando o comportamento (útil para bugs intermitentes)
  • Logs: Erros do console, logs do servidor
  • Network requests: Capturas de requisições HTTP falhando
  • Arquivos: Arquivos que causaram o problema, se aplicável

Ferramentas recomendadas:

  • Lightshot, ShareX, Snipping Tool para screenshots
  • OBS, ShareX, Loom para gravação de vídeo
  • DevTools do navegador para logs e network

5. Prioridade e Severidade

Classifique o bug de acordo com o impacto no sistema e usuários:

Severidade

Indica o impacto técnico do bug:

  • Crítica: Sistema inutilizável, crash, perda de dados
  • Alta: Funcionalidade principal quebrada, mas sistema ainda usável
  • Média: Funcionalidade secundária afetada, workaround disponível
  • Baixa: Problema cosmético ou menor, não afeta funcionalidade

Prioridade

Indica a urgência de correção baseado em impacto de negócio:

  • Urgente: Deve ser corrigido imediatamente
  • Alta: Deve ser corrigido o mais rápido possível
  • Média: Deve ser corrigido em um prazo razoável
  • Baixa: Pode ser corrigido quando houver tempo

Boas Práticas de Reporte

Seja Específico

Evite descrições vagas. Seja preciso sobre onde, quando e como o bug ocorre. Use termos técnicos quando apropriado, mas mantenha clareza.

Um Bug por Report

Não misture múltiplos bugs em um único report. Cada problema deve ter seu próprio ticket para facilitar rastreamento e correção.

Verifique se Já Existe

Antes de criar um novo report, verifique se o bug já foi reportado. Se sim, adicione informações adicionais ao report existente ao invés de criar um duplicado.

Use Templates

Muitas ferramentas (Jira, Bugzilla, etc.) têm templates. Use-os para garantir consistência e que nenhuma informação importante seja esquecida.

Seja Objetivo e Profissional

Mantenha um tom profissional. Foque nos fatos e evite julgamentos ou críticas. O objetivo é resolver o problema, não culpar alguém.

Inclua Informações de Rastreamento

Se possível, inclua informações que ajudem desenvolvedores a encontrar o código relacionado:

  • URL ou rota onde o problema ocorre
  • IDs de elementos relacionados
  • Mensagens de erro completas
  • Stack traces (se disponíveis)
