O que é BDD (Behavior-Driven Development)?

Definição

BDD (Behavior-Driven Development) é uma metodologia de desenvolvimento de software que enfatiza a colaboração entre desenvolvedores, QAs e stakeholders não técnicos. O BDD foca em descrever o comportamento do software em linguagem natural, facilitando a comunicação e garantindo que todos entendam o que está sendo desenvolvido e testado.

O BDD foi criado por Dan North como uma evolução do TDD (Test-Driven Development), com o objetivo de tornar os testes mais legíveis e compreensíveis para pessoas não técnicas.

Princípios Fundamentais do BDD

  • Linguagem Ubíqua: Usa uma linguagem comum que todos podem entender, reduzindo ambiguidades e mal-entendidos
  • Foco no Comportamento: Descreve o que o sistema deve fazer, não como fazer tecnicamente
  • Colaboração: Envolve desenvolvedores, QAs e stakeholders na definição de requisitos
  • Documentação Viva: Os cenários servem como documentação executável e sempre atualizada
  • Especificação por Exemplo: Usa exemplos concretos para descrever comportamentos

Gherkin - A Linguagem do BDD

O que é Gherkin?

Gherkin é uma linguagem estruturada em texto simples que permite descrever comportamentos de software de forma legível tanto para humanos quanto para máquinas. É a linguagem padrão usada pelo Cucumber e outras ferramentas BDD.

Gherkin usa palavras-chave específicas (Feature, Scenario, Given, When, Then, etc.) para estruturar cenários de teste de forma clara e padronizada.

Estrutura Básica de um Cenário Gherkin

Feature: Nome da funcionalidade
  Como [tipo de usuário]
  Eu quero [ação]
  Para [benefício]

  Scenario: Descrição do cenário
    Given [estado inicial]
    When [ação realizada]
    Then [resultado esperado]

Palavras-chave do Gherkin

  • Feature: Descreve a funcionalidade ou regra de negócio sendo testada
  • Scenario: Descreve um caso de teste específico
  • Given: Define o estado inicial ou pré-condições (contexto)
  • When: Descreve a ação ou evento que dispara o comportamento
  • Then: Define o resultado esperado ou validação
  • And / But: Permitem continuar steps do mesmo tipo sem repetir a palavra-chave
  • Background: Define steps comuns a todos os cenários de uma feature
  • Scenario Outline: Permite testar o mesmo cenário com diferentes dados
  • Examples: Fornece dados para Scenario Outline em formato de tabela
  • Rule: Agrupa cenários relacionados a uma mesma regra de negócio

Exemplos Práticos de Gherkin

Cenário Simples

Feature: Login de usuário
  Como usuário do sistema
  Eu quero fazer login
  Para acessar minha conta

  Scenario: Login com credenciais válidas
    Given que o usuário está na página de login
    When o usuário preenche email e senha corretos
    Then o usuário deve ser redirecionado para o dashboard
    And deve aparecer uma mensagem de boas-vindas

Cenário com Background e Scenario Outline

Feature: Processamento de pedidos
  Como vendedor
  Eu quero processar pedidos
  Para entregar produtos aos clientes

  Background:
    Given que o sistema está operacional
    And existe um catálogo de produtos disponível

  Scenario Outline: Aprovação automática de pedidos
    Given que existe um pedido com valor de "<valor>"
    And o cliente tem histórico de pagamento "<historico>"
    When o sistema processa o pedido
    Then o pedido deve ser "<status>"

    Examples:
      | valor | historico | status    |
      | 500   | em dia    | aprovado  |
      | 1500  | em dia    | pendente  |
      | 500   | atrasado  | pendente  |

O que é Cucumber?

Introdução ao Cucumber

Cucumber é uma ferramenta open-source que suporta BDD. Ele permite escrever testes em Gherkin e executá-los automaticamente. O Cucumber lê especificações escritas em linguagem natural e as traduz em código executável através de step definitions.

O Cucumber foi criado para facilitar a comunicação entre equipes técnicas e não técnicas, permitindo que stakeholders participem ativamente da definição de requisitos e testes.

Como o Cucumber Funciona

  1. Escreva cenários em Gherkin: Descreva comportamentos em linguagem natural usando a sintaxe Gherkin em arquivos .feature
  2. Crie Step Definitions: Implemente o código que executa cada step (Given, When, Then) em sua linguagem de programação preferida
  3. Execute os testes: O Cucumber lê os arquivos .feature, encontra as step definitions correspondentes e executa os testes
  4. Analise os resultados: O Cucumber gera relatórios mostrando quais cenários passaram ou falharam, facilitando a identificação de problemas

Benefícios do Cucumber e BDD

  • Documentação Viva: Os cenários servem como documentação sempre atualizada e executável
  • Colaboração: Facilita comunicação entre equipes técnicas e não técnicas
  • Clareza: Cenários escritos em linguagem natural são fáceis de entender
  • Rastreabilidade: Cada cenário está diretamente ligado a um requisito ou regra de negócio
  • Reutilização: Steps podem ser reutilizados em múltiplos cenários
  • Validação Contínua: Garante que o software sempre atende aos comportamentos especificados

Boas Práticas em BDD

1. Use Linguagem de Negócio

Evite termos técnicos. Escreva cenários que stakeholders não técnicos possam entender.

Bom: "Quando o usuário submete o formulário de cadastro"

Ruim: "Quando a API recebe um POST request no endpoint /users"

2. Foque no Comportamento, Não na Interface

Descreva o que acontece, não como interagir com elementos de UI. Isso torna os testes mais resilientes a mudanças na interface.

Bom: "Quando o usuário faz login"

Ruim: "Quando o usuário clica no botão de login com ID 'btn-submit'"

3. Mantenha Cenários Independentes

Cada cenário deve poder ser executado isoladamente. Use Background para pré-condições comuns entre cenários.

4. Use Scenario Outline para Dados Variados

Quando precisar testar o mesmo comportamento com diferentes dados, use Scenario Outline ao invés de criar múltiplos cenários separados.

5. Given-When-Then na Ordem Correta

Sempre mantenha a ordem: Given (estado) → When (ação) → Then (resultado). Esta ordem reflete o fluxo natural do comportamento e facilita a leitura.

6. Um When por Cenário

Cada cenário deve testar uma única ação. Se precisar de múltiplas ações, considere dividir em cenários separados ou usar And para ações relacionadas.

7. Then é Obrigatório

Todo cenário deve ter pelo menos um Then para validar o resultado esperado. Sem validação, não há como confirmar se o comportamento está correto.

Ferramentas e Recursos

Ferramentas BDD

  • Cucumber: A ferramenta mais popular para BDD, suporta múltiplas linguagens (Java, JavaScript, Ruby, Python, etc.)
  • SpecFlow: Implementação do Cucumber para .NET
  • Behave: Framework BDD para Python
  • JBehave: Framework BDD para Java
  • Gauge: Framework de testes open-source que suporta BDD
